THE RENDER LOOP

ALTITUDE 1 — lit-ui-router 1.9.0 · the client circuit · REV D: the loop routed on the iso grid

GENERAL NOTES

Why redraw a 2D loop in 3D: the cycle itself is flat, but the third axis is free to carry the relations flat arrows kept fumbling. Containment: the child <ui-view> literally stands on its parent's roof — nesting is stacking, not a box-in-a-box. Propagation: uiSrefTarget events rise past the document's plates to the uiSrefActive perch, which is how link tracking works — no registry, just bubbling. Instrumentation: TransitionController is a skybridge that taps the hall without standing on the route.

The document breaks the metaphor on purpose. Every other station is a building; the document is drawn the way Firefox's old Tilt inspector drew it — a browser window whose DOM rises as stacked plates by depth, window → body → app shell → <ui-view> content → the <a> element on top. It is the one structure on this sheet that really is layered, so it alone earns the literal treatment.

Service discovery is still DOM events. A nested view finds its parent with a composed context CustomEvent; every uiSref announces its targetState upward. The document tree is the dependency graph — which is exactly why the drawing can stand everything in one window.

The five doors are one seam. The bare entry registers custom elements as a side effect; ./pure is the same API with registration torn off. sideEffects in the manifest names exactly the four register files.

THE FAMILY SPINE

ALTITUDE 4 — one core, four living adapters, four dormant instruments · REV B: the spine re-massed from sloc × files, authored source counted 2026-08-16

GENERAL NOTES

Method — one basis for every member. Authored source, not shipped bundles: each upstream package was shallow-cloned from its ui-router org repository on 2026-08-16 (every HEAD happened to be the published version drawn here), and this repo's members were read from packages/*/src. Counted files are .ts/.tsx/.js under src/; *.d.ts, specs/ and __tests__/, and typedoc stub modules are excluded. sloc is lines that are neither blank nor comment-only. Twelve packages, 207 authored files, 13,614 lines.

An isometric city would still lie here. Adjacent blocks imply interaction, and the adapters have none — each rib touches only the spine. So the plan stays radial and the new ink is mass: block width ∝ √sloc, block height ∝ file count, which lets a two-file, 233-line package like sticky-states read as the sliver it is beside core's 80-file slab. Core alone is 5,272 lines — 39% of the family's authored mass, and more than the four adapters combined.

The gates disagree, and that is the finding. Every limb declares a range on @uirouter/core, drawn here as a hatched tablet where the limb's stem crosses toward the rail. The dormant instruments still admit core 5 (>=5.0.0, >=5.0.1); rx admits >=6.0.1; angularjs and angular carets on ^6.1.2; this repo's four packages sit on ^6.0.8. One gate is red: @uirouter/react pins core at exactly 6.1.2 and ships it as a dependency, not a peer — the only limb that can install a second copy of the state machine into a consumer's tree, and the only one that cannot be moved forward without a react release.

Mass does not track liveness. The largest limb on the sheet is the dormant @uirouter/visualizer (34 files, 2,018 lines, quiet since 2020) — it carries a preact/d3 rendering stack, so it out-masses every living adapter. The newest limb, lit-ui-router, is 12 files and 1,189 lines, and it is the only limb growing limbs of its own: the companion bay adds another 1,379 lines behind a single shared gate, with lit-ui-router-mobx the one package on this sheet that peers a limb rather than the spine.

THE DESIGN SPACE

ALTITUDE 5 — routers in the JS runtime · positions are editorial, argued in the notes

GENERAL NOTES

This altitude forbids the city outright. A diagram's edges assert mechanism, and there is none between TanStack and SvelteKit. The honest form is a positioned chart whose axes are real, contested design decisions — with the positions owned as editorial judgment, not measurement.

Reading the columns: the field has been sliding left for a decade — filesystem routes and typegen move matching toward build time; server components move it toward the server. The client-runtime column is where the platform itself now competes, via the Navigation API.

The square is the argument. Every circle on this chart treats the URL as the source of truth and derives the view from it. The ui-router lineage inverts that: a named, hierarchical state tree is primary, and the URL is a projection — one of several possible addresses for a state. That inversion is why sheet 1's loop runs through a state registry rather than a path matcher, and why the same tree can answer HTTP requests in sheet 2's server lane. It is also why the square sits alone: the niche is real, small, and — for state-heavy embedded UIs where the address bar is not the whole story — defensible.

THE ROUTING STRATA

ALTITUDE 6 — routing in general · the altitude where prose outranks pictures

GENERAL NOTES

The definition that survives every stratum: a router is an address space, a matching function, and transition semantics. BGP matches prefixes and forwards with no memory; an HTTP framework matches path patterns into a stateless response; an edge ruleset rewrites and proxies; a SPA router matches a URL into a view tree through a cancellable lifecycle; a state router matches into a named hierarchy through guarded, resolving transitions.

What changes with ascent is the transition. At the bedrock a transition is a forwarding decision that forgets itself immediately. Each stratum upward, transitions acquire more: statefulness, interceptability, cancellation, resolved data, meaning. By the surface a transition is a first-class object with a lifecycle — which is precisely the layer sheet 1 drew.

Why this sheet is mostly writing: no mechanism spans these strata — an IP hop and a ui-view activation share a definition, not a wire. Drawing more than a core sample here would be decoration, and the reference's own rule applies: the drawing earns exactly as much ink as the mechanism deserves.

THE DELIVERED CITY

ALTITUDE 1½ — what npm actually installs for one consumer · sample-app-lit-vanilla · REV B: recounted after the lodash-es swap · 2026-08-16

GENERAL NOTES

Method: the production closure of apps/sample-app-lit-vanilla (dependencies plus installed peers — pnpm auto-installs peers, so they are genuinely on disk), resolved through the pnpm store and measured as delivered: lines of .js/.ts/.css/.html per package directory, source maps and prose excluded, .d.ts drawn separately as the hatched annex. Workspace-linked members are measured by their built dist/ — the shape a registry install would deliver. Plenty of prior art measures this differently — bundlephobia and packagephobia weigh tarballs and install bytes, npmgraph draws the dependency graph — but this sheet measures what actually lands on disk, in files and lines, and stages it as a city with the consumer’s own building standing in it for scale.

The consumer is a doormat in its own city. The app brings 597 lines of its own and receives 190,122 delivered lines of code plus 47,488 of type declarations — 318× its own mass. The router this repo exists to ship, lit-ui-router, delivers 798 lines: one of the smallest buildings on the skyline it anchors.

The drawing changed the city. Rev A drew lodash 4.18.1 as the tallest building on the skyline — 45,205 lines, 1,048 files, delivered for four imports (isEqual, cloneDeep, get, set). That finding became PR #604: the swap to lodash-es halved the building to 22,193 lines and 644 files, dropping it to fourth place behind dompurify, hono, and @uirouter/core. The bundler always tree-shook the wire cost — sheet 9 charts that collapse, 25 KB → 4 KB — but the delivered city is what installs, audits, and updates, and it is 23,000 lines lighter.

The demo chrome ships a second, complete lit. lit-dialog and the api-viewer panels pin the lit 2 era, so lit, lit-html, lit-element, and @lit/reactive-element are each delivered twice (2.8.0/3.3.3 side by side) — twin pairs on the skyline. And hono (30,489 lines) stands here because ui-router-server names it a peer: a server framework delivered into a client demo by peer auto-install.

Note the vertical scale: 1 px ≈ 250 lines against sheet 7’s ≈ 34. Drawn at the workspace’s own scale, even the halved lodash-es would stand 653 px tall — the compression is the finding.

GENERAL NOTES

Method: a generateBundle census on the real production vite build of sample-app-lit-vanilla — output chunk hashes identical to the deployed dist, so this is the deploy itself, not a reconstruction. Every rendered module is attributed to its package; footprint is post-tree-shake source kept, height is each module scaled by its own chunk's minify and gzip ratios — the honest wire share. Beside it, the repo's own codecov bundle-analysis probe (tools/bundle-probe, the <pkg>-<label>-esm series CI uploads) is recomputed locally to price each exported entry. The library is a skin over the machine. The biggest building in the bundle is not the router package — it is @uirouter/core at 28.8 KB gz, 26% of the wire. lit-ui-router itself is the small accent building: 4.6 KB, 3.7%. THE ENTRY QUARTERS

ALTITUDE 2⅞ — the same wire, cut by published package · every exported entry priced alone · counted 2026-08-16

GENERAL NOTES

Method: the same probe as sheet 10's doors strip, run to completion: every exported entry of the four publishable packages bundled alone with rolldown — minified, declared dependencies and peers external — which is the price a consumer's bundler pays at that door, and byte-for-byte the <pkg>-<label>-esm series CI uploads to codecov. Footprint is minified bytes, height gzipped. Sheet 10 is the unified view — one real app's bundle with all of these mixed by the bundler; this sheet cuts the same machinery by published package and entry point. The quarters don't sum and shouldn't: doors overlap (./pure is . minus registration), which is exactly what the split view exists to show.

The twin towers are one building with two doors. . and ./pure differ by 89 gzipped bytes — the whole cost of custom-element registration. The register economics run the other way: the two one-element doors sum to 3,338 gz while the umbrella ./register is 2,288, because each element door carries the shared element core with it. Take the umbrella or one element door; taking two per-element doors ships the core twice.

The server is a storefront, not a tower. Eight doors: an index that prices within 12 bytes of lit-ui-router's flagship (4,965 vs 4,953 — coincidence, but a tidy one), redirect and matcher wings, and four framework adapters — hono, fetch, vite, connect — packed within 72 bytes of one another: thin skins over one core. ./simulate, the test double, is 283 bytes.

Plugins price like footnotes. The entire mobx reactivity layer enters at 650 gz and the navigation-location plugin at 670 — each cheaper than the gap between ./register and its two element doors. The expensive thing in this family is never the adapter; it is the state machine they all defer to, and that machine (sheet 10's 28.8 KB @uirouter/core) is external here by design.

Why both views exist. The split view is the seller's ledger — what each door costs at the threshold. The unified view is the buyer's receipt — what one app's bundler actually made of them (it paid 4,552 of the flagship's 4,953). Codecov tracks the ledger per commit; sheet 10 audits the receipt.
