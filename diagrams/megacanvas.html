THE RENDER LOOP

ALTITUDE 1 — lit-ui-router 1.9.0 · the client circuit · REV C: the document drawn as a DOM layer stack

GENERAL NOTES

Why redraw a 2D loop in 3D: the cycle itself is flat, but the third axis is free to carry the relations flat arrows kept fumbling. Containment: the child <ui-view> literally stands on its parent's roof — nesting is stacking, not a box-in-a-box. Propagation: uiSrefTarget events rise past the document's plates to the uiSrefActive perch, which is how link tracking works — no registry, just bubbling. Instrumentation: TransitionController is a skybridge that taps the hall without standing on the route.

The document breaks the metaphor on purpose. Every other station is a building; the document is drawn the way Firefox's old Tilt inspector drew it — a browser window whose DOM rises as stacked plates by depth, window → body → app shell → <ui-view> content → the <a> element on top. It is the one structure on this sheet that really is layered, so it alone earns the literal treatment.

Service discovery is still DOM events. A nested view finds its parent with a composed context CustomEvent; every uiSref announces its targetState upward. The document tree is the dependency graph — which is exactly why the drawing can stand everything in one window.

The five doors are one seam. The bare entry registers custom elements as a side effect; ./pure is the same API with registration torn off. sideEffects in the manifest names exactly the four register files.

THE INSTRUMENT YARD

ALTITUDE 3 — 4 publishable packages · 16 tools · ~38 turbo tasks · one packer, many readers

GENERAL NOTES

The reference's thesis is truest at this altitude. "Nearly every hard problem turned out to be a measurement problem" describes this repo exactly: four publishable packages, sixteen tools/* instruments. The city is mostly instruments; the product is one crate (structure 6).

One packer, many readers (#449). Every check reads the same cached packPublishTarball output — check:exports (publint + attw), dts-backtest, bundle probes, published-diff. No check re-packs, so a drift verdict is always about the artifact that would actually ship.

Height = what halts. Low slabs report (peer-floor tier-1 never gates a PR). Mid towers gate merges. The one red-capped tower, published-diff (9), halts publishing itself — and it closes the loop by pulling the live npm tarball back for comparison, which makes the registry part of the circuit rather than a destination.

Two gantries, one site. mise runs the site node-free from a standalone umbrella; turbo fans the same tasks out with remote caching. Known failure mode, drawn nowhere but written here as a real condition: a poisoned remote cache entry can replay a stale verdict — --force is the remediation.

THE DESIGN SPACE

ALTITUDE 5 — routers in the JS runtime · positions are editorial, argued in the notes

GENERAL NOTES

This altitude forbids the city outright. A diagram's edges assert mechanism, and there is none between TanStack and SvelteKit. The honest form is a positioned chart whose axes are real, contested design decisions — with the positions owned as editorial judgment, not measurement.

Reading the columns: the field has been sliding left for a decade — filesystem routes and typegen move matching toward build time; server components move it toward the server. The client-runtime column is where the platform itself now competes, via the Navigation API.

The square is the argument. Every circle on this chart treats the URL as the source of truth and derives the view from it. The ui-router lineage inverts that: a named, hierarchical state tree is primary, and the URL is a projection — one of several possible addresses for a state. That inversion is why sheet 1's loop runs through a state registry rather than a path matcher, and why the same tree can answer HTTP requests in sheet 2's server lane. It is also why the square sits alone: the niche is real, small, and — for state-heavy embedded UIs where the address bar is not the whole story — defensible.

THE ROUTING STRATA

ALTITUDE 6 — routing in general · the altitude where prose outranks pictures

GENERAL NOTES

The definition that survives every stratum: a router is an address space, a matching function, and transition semantics. BGP matches prefixes and forwards with no memory; an HTTP framework matches path patterns into a stateless response; an edge ruleset rewrites and proxies; a SPA router matches a URL into a view tree through a cancellable lifecycle; a state router matches into a named hierarchy through guarded, resolving transitions.

What changes with ascent is the transition. At the bedrock a transition is a forwarding decision that forgets itself immediately. Each stratum upward, transitions acquire more: statefulness, interceptability, cancellation, resolved data, meaning. By the surface a transition is a first-class object with a lifecycle — which is precisely the layer sheet 1 drew.

Why this sheet is mostly writing: no mechanism spans these strata — an IP hop and a ui-view activation share a definition, not a wire. Drawing more than a core sample here would be decoration, and the reference's own rule applies: the drawing earns exactly as much ink as the mechanism deserves.

THE DELIVERED CITY

ALTITUDE 1½ — what npm actually installs for one consumer · sample-app-lit-vanilla · counted 2026-08-16

GENERAL NOTES

Method: the production closure of apps/sample-app-lit-vanilla (dependencies plus installed peers — pnpm auto-installs peers, so they are genuinely on disk), resolved through the pnpm store and measured as delivered: lines of .js/.ts/.css/.html per package directory, source maps and prose excluded, .d.ts drawn separately as the hatched annex. Workspace-linked members are measured by their built dist/ — the shape a registry install would deliver. Plenty of prior art measures this differently — bundlephobia and packagephobia weigh tarballs and install bytes, npmgraph draws the dependency graph — but this sheet measures what actually lands on disk, in files and lines, and stages it as a city with the consumer’s own building standing in it for scale.

The consumer is a doormat in its own city. The app brings 597 lines of its own and receives 213,050 delivered lines of code plus 47,435 of type declarations — 357× its own mass. The router this repo exists to ship, lit-ui-router, delivers 743 lines: one of the smallest buildings on the skyline it anchors.

lodash is the largest building: 45,205 lines, 1,048 files — for four imports. The whole workspace uses isEqual, cloneDeep, get, set. The bundler tree-shakes what ships to the browser, but the delivered city is what installs, audits, and updates.

The demo chrome ships a second, complete lit. lit-dialog and the api-viewer panels pin the lit 2 era, so lit, lit-html, lit-element, and @lit/reactive-element are each delivered twice (2.8.0/3.3.3 side by side) — twin pairs on the skyline. And hono (30,489 lines) stands here because ui-router-server names it a peer: a server framework delivered into a client demo by peer auto-install.

Note the vertical scale: 1 px ≈ 250 lines against sheet 7’s ≈ 34. Drawn at the workspace’s own scale, lodash would stand 1,330 px tall — the compression is the finding.
